# Workflow scope

These files are task-selected methods. Their presence is not a standing job,
permission to publish/delete, or a reason to run them all before development.
Follow the user's current scope and the target project's AGENTS first.

| Workflow | Use when | Scope/permission boundary |
| --- | --- | --- |
| `fitness-ledger-maintenance.md` | FL source maintenance | Current FL routing, tests and closeout take precedence |
| `fitness-ledger-backup-and-rollback.md` | Requested checkpoint/recovery | Git source and formal data are different targets; no automatic Push |
| `fitness-ledger-wechat-readonly-release.md` | Mini/cloud changes requiring that release | Run only affected steps; cloud deployment/upload needs authorization |
| `generate-and-clean-old-versions.md` | Replacement/cleanup belongs to the task | Creating an artifact does not authorize deleting other user files |
| `project-first-python-learning-and-tool-building.md` | The user asks to learn through a project | Do not turn a requested fix into homework or force a learning checkpoint |
| `plugin-lab.md` | The user asks for a plugin experiment | Ordinary implementation does not require plugin exploration |
| `idea-to-issues.md` | The user wants an idea split into deliverable work | Draft locally first; sending/publishing issues requires explicit scope |
| `weekly-review.md` | The user requests a review | No scheduled execution or memory writes merely because a week passed |
| `automation-map.md` | The user asks to design/configure automation | Proposals are not installed jobs; actual creation follows app tools and authorization |

Memory/decisions are historical context unless maintained as current rules.
Read only relevant entries. Write memory only when explicitly requested and
through the applicable memory-write mechanism; do not add a memory-update or
confirmation ritual to every task. Do not reinterpret an old workflow's broad
imperative as fresh authorization for an external or destructive action.
